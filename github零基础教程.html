第一章

专业名词大扫盲：把"黑话"讲成人话

这一章是整份教程的"字典"。里面每一个词，都是你在接触 Git / GitHub 时会撞上的。别急着背，先读一遍混个脸熟，操作到哪一步再回来查，自然就记住了。

1.1 三个绕不开的名字：Git、GitHub、版本控制

很多教程上来就甩术语，把人绕晕。其实只要记住这三兄弟的分工，后面全通：

  • 版本控制（Version Control）：是一种"思想/方法"——帮你记录文件每一次改动、随时回到任意历史版本。类比：游戏存档。每过一关存一次，想重玩哪关都行。
  • Git：是"工具"。安装在你自己电脑上的免费软件，专门负责在本机做版本控制。类比：电脑里自带的"存档管理软件"，只管你这台电脑。
  • GitHub：是"网站/平台"。把用 Git 管理的项目放到网上，能备份、能分享、能多人协作。类比：带时间机的网盘 + 程序员朋友圈。
一句话记住 Git 管"怎么记"（本地工具），GitHub 管"放哪、给谁看"（网上平台），版本控制是它们共同做的事。后面所有术语，都是围绕"本地存档 + 云端同步"这两个动作展开的。

下面按主题分成 8 组。用上面的搜索框输入中文、英文或关键词（比如"分支""commit""冲突"），卡片会自动筛选，特别方便以后当字典查。

核心概念：版本控制三兄弟与仓库

版本控制Version Control

一种"记录文件每次改动"的方法，能随时回到以前任意一个版本，还能看出每次改了什么、谁改的。

类比：游戏存档，每到一个节点存一次，想回哪一关都行。

GitGit

安装在你自己电脑上的免费软件，负责在你电脑上做版本控制，是这一切的"本地引擎"。

类比：电脑里的存档管理软件，只管你这台机器。

GitHubGitHub

一个存放、分享、协作管理项目的网站。把你的项目放上去，既能云端备份，也能给别人看、一起改。

类比：带时间机的网盘 + 程序员朋友圈。

仓库Repository

一个项目以及它的全部修改历史所在的地方，缩写叫 repo。Git 的一切操作都发生在一个个仓库里。

类比：带历史记录的"项目文件夹"。

本地仓库Local Repository

存在你自己电脑硬盘上的那份仓库，平时干活、存档都在这里。

类比：电脑里的"原稿文件夹"。

远程仓库Remote Repository

存在 GitHub 网站上的那份仓库，是云端的备份，也能共享给别人、一起协作。

类比：网盘上的同步文件夹，本地丢了还能恢复。

提交Commit

把当前所有改动"拍一张照"存起来，记录谁、在什么时候、改了什么。这是 Git 里最重要的动作。

类比：游戏里点"保存进度"，之后随时能回到这一刻。

暂存区Staging Area

提交之前，先放"准备这次一起存档的文件"的一个中间区域。你可以挑一部分文件提交，不用每次都全存。

类比：打包行李时的"待装行李箱"，先放进去，最后一起托运（提交）。

add（添加）git add

把文件放进暂存区的动作。命令是 git add 文件名。只有被 add 过的文件，才会进入下一次提交。

类比：把要带的行李一件件装进行李箱。

快照Snapshot

每次提交那一刻，所有文件内容被完整记录下来的"即时照片"。Git 靠快照实现"回到过去"。

类比：给房间拍照留档，照片记录的是拍照那一刻的样子。

分支与协作：平行宇宙、合并与申请

分支Branch

从主线复制出来的一个独立工作区，在里面随便改、随便试，不影响主线。改满意了再合并回去。

类比：平行宇宙 / 草稿本，写坏了扔掉，正式本不受影响。

主分支main / master

项目默认的那条主线，通常放稳定、正式的版本。新项目叫 main，老项目叫 master，一回事。

类比：最终定稿的"正式文档"。

合并Merge

把一个分支的改动合回另一个分支，让两条线的历史重新并到一起。

类比：把草稿本上的修改誊写进正式文档。

冲突Conflict

两个人改了同一处内容，Git 不知道该听谁的，就停下来请你"拍板"。这是正常现象，不是报错。

类比：两份答案不一样，需要你决定保留哪份。

拉取请求Pull Request

向项目主人申请"把我分支的改动合并进主线"，缩写 PR。团队协作和开源贡献都靠它。

类比：交作业给老师批改，通过后才记入正式成绩。

Fork（派生）Fork

把别人的仓库整个复制一份到你自己名下，变成"你的副本"，随便改，不影响原项目。

类比：把别人家的菜谱抄一份带回家，在家随便改良。

上传与下载：克隆、推送、拉取

克隆Clone

把远程仓库完整地下载到你电脑上，包含它的全部修改历史。拿到一个项目，第一步通常是 clone。

类比：把网盘整个文件夹复制到电脑。

推送Push

把你本地新产生的提交，上传到远程仓库。做完这步，GitHub 上就能看到你的改动了。

类比：把电脑文件上传到网盘。

拉取Pull

把远程仓库的最新改动下载到本地，和本地合并。别人更新了项目，你 pull 一下就能同步。

类比：把网盘更新过的内容同步到电脑。

社区互动：Star、Issue、Release 等

Star（星标）Star

给项目点"赞/收藏"，表示喜欢、以后好找。星标数越高，通常代表项目越受欢迎。

类比：朋友圈点赞 + 收藏。

Watch（关注）Watch

关注某个项目，它一有动态（新提交、新 Issue、新 Release）就会通知你。

类比：订阅了某个公众号，更新会推送给你。

Issue（议题）Issue

项目里的"问题工单"，用来报 bug、提建议、发起讨论，每条都有编号可以引用。

类比：意见箱 / 留言板。

Release（发布版）Release

项目正式发布的一个版本，别人可以下载到对应时点的代码或安装包，通常配一个版本号。

类比：官方发布的"安装包"。

Tag（标签）Tag

给某一次提交贴一个标签，比如 v1.0.0，方便快速定位到某个重要版本。

类比：书签，一翻就找到那个版本。

Milestone（里程碑）Milestone

把一批 Issue 归到同一个目标节点下，表示这些任务都是在为同一个目标服务。

类比：项目进度表上的里程碑。

项目文件与开源：README、Markdown、License

READMEREADME

项目首页最显眼的"说明书"，介绍这个项目是干什么的、怎么安装、怎么用。打开仓库第一眼看到的就是它。

类比：产品的说明书 + 门面。

MarkdownMarkdown

一种很简单的排版语言，用几个符号就能写出标题、列表、加粗、链接。README 就是用它写的。

类比：用"快捷键"排版，写完自动变漂亮。

License（开源协议）License

一份说明别人"能用你的代码做什么、不能做什么"的文件。开源项目通常必须配一个。

类比：贴在门口的"使用须知"。

开源Open Source

代码公开，任何人都能看、能学、能改、能提建议，还能在其他项目里使用。

类比：公开的菜谱，谁都能学，还能改良后分享给别人。

连接与安全：SSH、HTTPS、Token、GPG

SSHSSH

一种加密的连接方式，用一对"钥匙"（公钥 + 私钥）安全地连接 GitHub。配一次，长期免输密码。

类比：门禁卡（公钥）+ 钥匙（私钥）。

HTTPSHTTPS

通过网址地址（用用户名 + 令牌）连接 GitHub 的方式。地址以 https://github.com 开头。

类比：用账号密码登录的方式。

Token（令牌）Personal Access Token

一串代替密码的专用字符串，用来访问你的 GitHub 账户，可以限定权限、随时撤销，比密码安全。

类比：某个 App 的"专用临时密码"。

GPGGPG

给提交"签名"，证明"这确实是我提交的、没被篡改过"。进阶功能，新手了解即可。

类比：在文件上盖一个专属电子印章。

电脑基础词：命令行、路径、目录、桌面

命令行 / 终端Terminal

一个黑底窗口，用打字的方式指挥电脑做事。Git 最常用的操作都是在这里输入命令完成的。

类比：和电脑"打字对话"，说一句它做一件。

路径Path

文件在电脑里的"地址"，例如 C:\Users\你的名字\Desktop。命令里常用它定位文件在哪儿。

类比：门牌号，告诉电脑去哪个文件夹找人。

目录Directory

就是"文件夹"，存放文件和子文件夹的地方。命令行里"进入目录"就是"打开文件夹"。

类比：书柜里的格子。

桌面Desktop

电脑开机后看到的那个主屏幕，它本身也是一个文件夹（一般在 C:\Users\你的名字\Desktop）。

类比：你的书桌桌面，随手放东西的地方。

进阶小工具：.gitignore、Pages、Actions

.gitignore.gitignore

一个"排除名单"文件，告诉 Git 哪些文件（比如临时文件、密码配置）不用管、不用上传。

类比：打包时的"不用装的东西清单"。

GitHub PagesGitHub Pages

GitHub 免费帮你托管静态网页，会生成一个公开网址，比如 你的用户名.github.io/项目名。

类比：免费送你的"网站服务器"，放个网页就能访问。

ActionsActions

项目里的自动化流程，比如每次提交代码后自动跑测试、自动发布。新手了解即可，以后慢慢玩。

类比：自动流水线 / 定时机器人。

第二章

注册 GitHub 账号，并认识它的界面

这一章全程在浏览器里操作，不用碰代码，先混个脸熟。

2.1 注册账号

  1. 打开 GitHub 官方网站

    在浏览器地址栏输入 github.com 并回车。看到页面右上角有一个 Sign up（注册）按钮，点击它。

  2. 填写邮箱、密码、用户名

    按页面提示依次填：

    • Email：填你常用的邮箱（QQ 邮箱、163、Gmail 都行），后面要收验证邮件。
    • Password：设置密码。GitHub 要求至少 8 位，并且要包含字母和数字。
    • Username：这是你的"网名"，会出现在你的个人主页地址里，例如 github.com/你的用户名。建议用简短、好记的英文（比如名字拼音）。想好再填，虽然之后能改，但改起来麻烦。

    中间可能让你完成一个简单的拼图验证，照着做就行。填完点 Create account。

  3. 去邮箱点验证链接

    GitHub 会给你刚填的邮箱发一封验证邮件。登录邮箱，找到它，点里面的 Verify email address 按钮。回到 GitHub 网页，可能让你再输入一次邮箱确认。

  4. 登录成功，进入"首页仪表盘"

    登录后你会看到一个面板（Dashboard）。先别急，我们先认识它。上面一行是导航，重点记住几个：

    • ＋ 号（右上角）：用来创建新仓库、新东西，后面经常用。
    • 铃铛：通知中心，别人 @ 你或提到你的项目时会响。
    • 头像：你的账户菜单，点开后里面有 Settings（设置），配 SSH 时要用。
💡 用户名很重要 你的开源项目地址会变成 github.com/你的用户名/项目名。用户名是你在 GitHub 世界的"门牌号"，选一个愿意长期用的。

2.2 认识仓库页面

在 GitHub 里，几乎所有工作都发生在一个个"仓库"页面里。打开任意一个仓库（比如点你自己的头像进入主页，再点你的项目），从上到下认识这些区域：

  • 代码区（Code）：仓库默认显示的就是这个页签，里面列出所有文件和文件夹，点开可以看代码内容。
  • README：如果项目根目录有 README 文件，会在文件列表下方直接渲染出来，是项目的"门面"。第一章讲过，还记得吗？
  • Issues：问题区，报 bug、提需求的地方。
  • Pull requests：合并申请区，协作的关键。
  • Actions：自动化流程区。
  • Settings：设置区，改仓库名字、删仓库、配 GitHub Pages 都在这里。
  • Code（绿色按钮）：在文件列表右上角，点开可以复制仓库地址（clone 时要用）。
⚠️ 常见混淆 有人以为"仓库"就是"项目"，其实差不多，但仓库 = 项目 + 完整修改历史。别人 Star 你的仓库，等于给"你的项目"点赞。

2.3 动手：创建你的第一个仓库（现在就可以做）

  1. 点右上角的 ＋ 号 → New repository（新建仓库）
  2. 填仓库名字

    Repository name 填一个英文名，例如 hello-world。可以加一句 Description（简介），不填也行。

  3. 选择公开还是私有

    Public（公开）：所有人都能看到——做开源项目选它。Private（私有）：只有你和邀请的人能看到。练习时选哪个都行。

  4. 勾选 Add a README file

    勾上它，GitHub 会自动帮你生成一个说明文件，仓库就不会是空的。然后点 Create repository。

恭喜！你有了人生第一个 GitHub 仓库。记住它的地址（github.com/你的用户名/hello-world），后面几章都会用到。

第三章

在 Windows 上安装并配置 Git

  1. 打开下载页

    浏览器打开 Git 官方下载页：git-scm.com/download/win。一般会自动识别你的系统，看到 64-bit Git for Windows Setup 就点它下载（现在电脑基本都是 64 位）。

第六章

分支与协作：branch、merge、Pull Request

这一章是 Git 最精彩的部分：学会开"平行宇宙"（分支），再学会把平行宇宙合回主线（合并），最后掌握团队协作的标准流程（Pull Request）。

6.1 什么是分支（复习 + 深入）

第一章讲过：分支 = 从主线复制出来的独立工作区，在里面随便改都不影响主线。这样你可以放心大胆地做实验：新功能写好了，合并回主线；写砸了，直接删掉，主线毫发无伤。

📌 分支类比 主线 main 是"正式出版的定稿"，分支是"草稿本/平行宇宙"。你在草稿本上随便写、随便改，改满意了再誊写（merge）进正式本。

  1. 查看当前分支

    在 project 文件夹的 Git Bash 里输入：

  2. 创建并切换到新分支

  1. 回到要"接收改动"的分支

6.4 冲突 Conflict：必经之路，别怕

如果两个分支改了同一处内容，Git 就不知道听谁的，会停下来让你"拍板"，这就是冲突。它是正常机制，不是错误。

  1. 制造一次冲突

    在 main 上把 README.md 某一行改成 A 内容并提交；再开分支改同一行为 B 内容并提交；切回 main 合并——Git 会提示 CONFLICT，并告诉你是哪个文件冲突。

  2. 打开冲突文件，你会看到这样的标记

    用编辑器打开冲突文件，会看到三块：

    <<<<<<< HEAD
主线里的内容（我本地的）
=======
分支里的内容（dev 带过来的）
>>>>>>> dev

    意思是：<<<<< 到 ======= 是"本地"的内容，======= 到 >>>>> 是"对方"的内容。

  3. 手动解决：保留你想要的，删掉其他

    删掉不要的内容，保留想要的，并且把那些 <<<<<、=======、>>>>> 标记行全部删掉，只留下最终结果。

  4. 重新 add + commit，完成合并

    git add 冲突文件名 → git commit -m "解决冲突"。搞定！冲突解决完毕。

💡 遇到冲突的心态 冲突 ≠ 你错了，而是"两个人同时改了同一处，需要一个人做决定"。绝大多数冲突几秒钟就能解决。记住流程：看标记 → 删多余 → add → commit。

6.5 团队协作的标准流程：Pull Request（PR）

在真实团队里，大家不会直接在 main 上乱改，而是走"分支 + PR"流程：

  1. 开一个分支做你的改动

    git checkout -b feature-新功能名，然后正常改、add、commit。

  2. 把分支推送到远程

    git push -u origin feature-新功能名。

  3. 去 GitHub 页面发起 PR

    打开仓库页面，会看到一个黄色提示条 Compare & pull request，点它。填写 PR 标题和说明（做了什么、为什么），点 Create pull request。

    PR 相当于"交作业申请"：你说"请把我这个分支合并进主线"。

  4. 负责人（或你自己）审核并合并

    在 PR 页面点 Merge pull request → 确认 Confirm merge。合并成功后，可以点 Delete branch 把远程分支删掉。

📌 PR = 交作业，Merge = 老师批改通过 在 GitHub 上，"Pull Request（拉取请求）"虽然名字带 Pull，但本质是"申请把你的改动合并进去"。团队协作时，代码先经过 PR 审核，再合入主线，这样安全又清晰。
第七章

Fork 和参与他人项目

你学 Python 的目标是做开源项目，而参与开源的第一步，往往就是先"加入别人的项目"。这一章教你用 Fork + Pull Request 参与任何公开项目。

7.1 什么是 Fork（回顾）

Fork = 把别人的仓库整个复制一份到你自己名下，变成"你的副本"。你可以在副本里随便改，完全不影响原作者的项目。

📌 类比 就像把别人家的菜谱整本抄一份带回家，在家随便改良；如果你觉得改良很好，就把改动"送回去"（发 PR），原作者可以选择接受。

7.2 Fork 一个项目

  1. 找一个你想参与的开源项目

    可以在 GitHub 首页搜索框里搜关键词，比如 "python tutorial" 或 "hello world"。找那种有 README、活跃度还不错的项目。

  2. 点右上角的 Fork 按钮

    在项目页面右上角，会看到 Fork 按钮，旁边有个数字（表示被 Fork 了多少次）。点它，确认 Fork 到你的账号，稍等片刻。

  3. 看效果

    刷新后，你会发现你的账号下多了一个同名仓库。它现在是你的了，随便改。

7.3 克隆你的 Fork 到本地

7.4 改代码，推送到你自己的 Fork

  1. 开分支（好习惯）

    进入项目文件夹，开一个分支：git checkout -b my-fix。

  2. 修改并提交

    正常改 → git add → git commit -m "修复了XX问题"。

  3. 推送到你的 Fork

    git push -u origin my-fix。现在你的 Fork 上有这个分支了。

7.5 发起 Pull Request 回原项目

  1. 在你的 Fork 页面点 Pull requests → New pull request

    GitHub 会显示你的 fork 与原项目的差异。

  2. 确认合并方向

    确认是"从你的 fork 的分支 → 原项目的主分支"，一般会自动选好。如果不对，点 base 和 compare 调整。

  3. 写清楚说明，创建 PR

    标题概括改动，说明里写"我改了什么、为什么、怎么验证"。然后点 Create pull request。

  4. 等待维护者审核

    原项目的维护者会看到你的 PR，可能直接合并，也可能让你修改（你推送新提交到同一分支，PR 会自动更新）。

⚠️ 保持你的 Fork 和原项目同步（进阶，了解即可） 原作者不断更新项目时，你的 Fork 会"落后"。想让自己的 Fork 跟上：在 GitHub 你的 Fork 页面点 Sync fork / Fetch upstream。或者在本地把原项目加为"上游"：git remote add upstream 原项目地址，之后 git pull upstream main 就能同步原项目的新改动。

7.6 开源贡献礼仪（小白也能做好）

  • 先读 README 和 CONTRIBUTING：很多项目专门写了"贡献指南"，先读再动手，事半功倍。
  • 从简单的 Issue 开始：找带 good first issue（新手友好）标签的问题，从修文档错字、补注释这类小事练手。
  • 改动小而清晰：一个 PR 只做一件事，说明写清楚，维护者更愿意通过。
  • 沟通要礼貌：用项目使用的语言（多数是英文），先说"你好"，问题描述清楚。
  • 心态放平：贡献的本质是"学习 + 利他"，被拒绝也很正常，收到反馈本身就是收获。

8.2 写一个像样的 README

一个开源项目的 README 就像它的"简历"，读者和贡献者都是先看它。建议包含这些部分（不一定要全，但"简介 + 用法"必须有）：

  • 项目名 + 一句话简介：我是干什么的，解决什么问题。
  • 功能特性：用 - 列表列 3～5 个亮点。
  • 安装 / 使用方法：别人拿到你的代码后，怎么运行？给出命令。
  • 使用示例：放几张截图（![说明](图片地址)）或一段运行结果。
  • 贡献方式：欢迎别人参与，写一句"欢迎提 Issue 和 PR"。
  • License：开源协议，写明别人能用你的代码做什么。
  • 作者 / 联系方式：你是谁，怎么联系你。

8.3 让 README 显示在仓库首页

把写好的 README.md 放到仓库根目录，git add + git commit + git push 后，刷新 GitHub 仓库页面，它会自动渲染在文件列表下方，还带目录。就这么简单。

8.4 GitHub Pages：免费发布你的网页

GitHub 能免费帮你托管静态网页，让你拥有一个形如 https://你的用户名.github.io/仓库名/ 的公开网址。非常适合给项目做展示页、做个人主页。步骤：

  1. 准备一个 index.html

    在仓库里新建一个 index.html（网页首页），写点内容，比如"你好，这是我的项目主页！"，然后 push 到 GitHub。

  2. 打开仓库 Settings → 左侧 Pages
  3. 选择发布源

    在 Source 那里选 Deploy from a branch，Branch 选 main，后面的下拉框选 /(root)，点 Save。

  4. 稍等片刻，访问你的网址

    等 1～2 分钟后刷新页面，上方会显示你的网址，打开它——你的个人网页上线了！

💡 成就感时刻 第一次看到自己的网页能被全世界访问，感觉非常棒。这是你从"学 Python 的小白"迈向"开源贡献者"的重要一步。

8.5 Release：发布正式版本

当你的项目稳定了，可以用 Release 发布正式版（如 v1.0.0），别人可以直接下载。步骤：

  1. 进入仓库的 Releases 区

    仓库页面右侧找到 Releases，点进去，再点 Create a new release。

  2. 创建版本标签

    点 Choose a tag，在输入框里填 v1.0.0，点 Create new tag on publish。Tag（标签）就是给某个时间点贴书签。

  3. 写发布说明

    标题填 v1.0.0，说明里写这一版新增了什么、修复了什么。

  4. 上传附件（可选）并发布

    可以把打包好的 .zip 等文件拖到 "Attach binaries" 区域。最后点 Publish release。

第九章

常见问题和解决环境（12 个高频坑）

以下是新手最容易踩的 12 个坑，全部按"现象 → 原因（大白话）→ 解决步骤"整理。出问题时点开对应条目，照着做就行。先别慌，报错不是世界末日，Git 的报错恰恰是它想帮你。

Q1 · 安装 Git 失败 / 装到一半出错
现象：双击安装包报错、进度条卡住或中途退出。
原因（大白话）：权限不够、下载的文件损坏、被杀毒软件拦截、磁盘空间不足，这几种最常见。
解决步骤：
  1. 右键安装包，选择"以管理员身份运行"。
  2. 重新去官网下载一次安装包（之前那个可能下载不完整）。
  3. 暂时关闭杀毒软件/防火墙后重试，装完再打开。
  4. 检查 C 盘剩余空间是否足够。
Q2 · 命令行找不到 git 命令
现象：输入 git --version 提示 'git' 不是内部或外部命令，或 bash: git: command not found。
原因（大白话）：Git 没装上，或者装了但"系统找不到它"（没加入环境变量 PATH）——就像家里有个工具箱但没告诉保姆它放在哪。
解决步骤：
  1. 先确认是否真的装过：去开始菜单搜 "Git Bash"，有就说明装上了，问题只是 PATH。
  2. 重新运行安装程序，在安装选项里，PATH 相关选项选默认的 Recommended（Git from the command line）。
  3. 装完后关掉旧窗口，重新打开 Git Bash再试。
  4. 仍不行：右键"此电脑" → 属性 → 高级系统设置 → 环境变量 → 在系统变量 Path 里添加 C:\Program Files\Git\cmd，确定后重开窗口。
Q3 · 中文乱码
现象：命令行里中文显示成乱码，或中文文件名变成 \346\226\207 这样的转义符号。
原因（大白话）：编码不一致。Windows 系统默认用 GBK/ANSI，而 Git 和 GitHub 用 UTF-8，两边"说话的口音"不一样。
解决步骤：
  1. 在 Git Bash 里执行下面这条经典命令，让中文文件名正常显示：
    $ git config --global core.quotepath false
  2. 文件内容用 UTF-8 编码保存：在 VS Code 右下角把编码切换成 "UTF-8"。
  3. 提交说明里写中文是没问题的，关键是文件和终端统一用 UTF-8。
Q4 · SSH 配置报错 / Permission denied (publickey)
现象：push 或 clone 时报 Permission denied (publickey)，连接不上。
原因（大白话）：GitHub 不认你这台电脑的钥匙。最常见是：公钥没复制完整、粘贴时多了空格、或地址用成了 HTTPS 却以为配好了 SSH。
解决步骤：
  1. 先测试：ssh -T git@github.com，看具体报错内容。
  2. 确认钥匙存在：ls ~/.ssh/，应看到 id_ed25519 和 id_ed25519.pub 两个文件。
  3. 重新 cat ~/.ssh/id_ed25519.pub 复制公钥，确认没漏字符，去 GitHub 的 Settings → SSH and GPG keys 检查是否粘贴正确。
  4. 确认你用的地址是 SSH 格式（git@github.com:...）而不是 HTTPS。
  5. 如果换了新电脑没生成钥匙，回到第五章 5.2 重新生成并添加公钥。
Q5 · 登录认证失败（GitHub 要求用 Token）
现象：push 时报 remote: Support for password authentication was removed. Please use a personal access token instead.
原因（大白话）：GitHub 出于安全，已经不允许用"密码"来 push 了，必须用一串专用的"令牌（Token）"当密码。
解决步骤：
  1. 生成 Token：GitHub 点头像 → Settings → 左下角 Developer settings → Personal access tokens → Tokens (classic) → Generate new token。
  2. 勾选 repo 权限（第一个大类），有效期随意，点 Generate 后立即复制保存（只显示一次）。
  3. push 时提示输用户名，填你的 GitHub 用户名；提示输密码处，粘贴这串 Token（不是真实密码）。
  4. 想一劳永逸，直接改用 SSH 方式（见第五章），连 Token 都不用再输。
Q6 · push 被拒绝（failed to push some refs / 非 fast-forward）
现象：push 时报 ! [rejected]、failed to push some refs，或提到 non-fast-forward。
原因（大白话）：远程仓库里有你本地没有的新提交（比如别人先推了，或你建仓库时勾了 README）。Git 保护规则：不能覆盖别人已有的内容，先同步再上传。
解决步骤：
  1. 先拉取远程更新：git pull（如有冲突按第六章 6.4 解决）。
  2. 或者用 git pull --rebase，把远程改动"垫"在你本地改动前面，历史更整洁。
  3. 解决完冲突后，再执行 git push 即可。
Q7 · 网络 / 代理问题（clone 或 push 超时）
现象：clone/push 一直卡住、报 timeout、unable to access、连接超时。
原因（大白话）：网络不稳定，或在国内访问 GitHub 时"路上堵车"，或电脑开了代理但 Git 不知道走代理。
解决步骤：
  1. 先换个网络试试（手机热点、不同运营商），这是最快的排查方法。
  2. 如果你开了代理软件，让 Git 也走代理（端口换成你软件里的端口）：
    $ git config --global http.proxy http://127.0.0.1:7890
  3. 取消代理：
    $ git config --global --unset http.proxy
  4. 加大超时时间，避免过早报错：
    $ git config --global http.lowSpeedLimit 0
$ git config --global http.lowSpeedTime 999999
  5. 克隆超大项目时可以尝试用加速镜像（注意只用于下载提速，不改你的远程地址）。
Q8 · Windows 换行符 CRLF 问题
现象：add 时提示 warning: LF will be replaced by CRLF 或反过来。
原因（大白话）：Windows 里"换行"习惯是回车+换行两个符号（CRLF），而 Linux/Mac 只用换行（LF）。Git 在两边自动"翻译"，就弹出了提示。
解决步骤：
  1. 这只是提示，不是错误，通常直接无视即可。
  2. 想统一，执行 git config --global core.autocrlf true（Windows 上推荐，Git 自动处理换行符）。
  3. 团队项目里通常有 .gitattributes 文件统一约定，跟着项目来就行。
Q9 · commit 忘加 -m，进了奇怪界面退不出去
现象：输入 git commit（没带 -m）后，进入一个黑乎乎的界面，按什么都没反应，很吓人。
原因（大白话）：你进入了 Vim 编辑器，Git 让你在这里写提交说明。它和老式的记事本不太一样，新手容易懵。
解决步骤：
  1. 按 i 键进入编辑状态（左下角会出现 INSERT），输入你的提交说明。
  2. 按 Esc 键退出编辑，输入 :wq 然后回车（保存并退出）。
  3. 想直接放弃本次提交：按 Esc，输入 :q! 回车（强制退出不保存）。
  4. 更省心的办法：以后都用 git commit -m "说明"，根本不会进这个界面。
Q10 · fatal: not a git repository
现象：输入任何 git 命令，报 fatal: not a git repository (or any of the parent directories)。
原因（大白话）：当前文件夹还不是仓库（没执行过 git init），或者你在错误的文件夹里打开了 Git Bash。
解决步骤：
  1. 用 pwd 看一下当前路径，确认你在项目文件夹里。
  2. 如果这确实是要做成仓库的文件夹，先执行 git init 初始化。
  3. 如果不是，用 cd 文件夹名 进入正确的文件夹再操作。
Q11 · 每次 push 都要输用户名密码
现象：明明配好了，但每次 push 还是提示输入账号密码。
原因（大白话）：你用的是 HTTPS 地址，且凭据没被记住。Windows 上 Git 默认会用"凭据管理器"帮你记住。
解决步骤：
  1. 执行 git config --global credential.helper manager，下次登录时勾选记住。
  2. 或者干脆改用 SSH 方式（推荐）：重新配好 SSH 后，把远程地址换成 SSH 格式 git remote set-url origin git@github.com:用户名/项目.git，一劳永逸。
Q12 · 改错了想反悔（撤销操作）
现象：改了文件想撤销，或提交错了想回退。
原因（大白话）：Git 给你准备了不同阶段的"后悔药"，但吃法要看你在哪个阶段。
解决步骤：
  1. 还没 add（改动还是"未暂存"）：git checkout -- 文件名，放弃对该文件的修改（注意：会丢失修改内容）。
  2. 已经 add 但还没 commit：git reset 文件名，把它撤出暂存区，改动还在。
  3. 已经 commit 想回退：git reset --hard HEAD~1，回退到上一个提交（慎用：会丢弃该提交及其改动）。
  4. 只想临时把手头改动收起来、先干别的：git stash（藏起来），之后用 git stash pop 取回。

结语 · 学完之后下一步做什么

恭喜你读到这里！现在你已经掌握了：

  • 把"黑话"翻译成人话的能力（第一章名词卡片随时可查）；

  • Fork 参与他人开源项目；
  • 用 README 和 GitHub Pages 展示项目、用 Release 发布版本。

下一步的四个建议：

  1. 把你在学的 Python 作业或小项目放上 GitHub：建仓库、写 README、发 v1.0.0，走一遍完整流程，你会非常有成就感。
  2. 每天 Star 一个喜欢的开源项目：逛一逛 GitHub 热门榜，看看优秀项目的 README 是怎么写的，慢慢就有感觉了。
  3. 找一个 good first issue 练手：从修文档错字开始，完成你的第一次开源贡献。
  4. 把这份教程存好：报错了就翻第九章，忘了命令就翻附录。教程不用背，用起来自然会熟。
💡 最后一句话 刚开始报错是很正常的，Git 的报错其实是在帮你。遇到问题，深呼吸，读一遍报错文字，再回来翻第九章——你离一个真正的开源贡献者，只差一个 commit 的距离。
